Rules:
- Return valid JSON only. Do not wrap it in Markdown. Do not add commentary.
- Use double quotes for all strings and keys.
- Use stable IDs:
  - Plan id: lowercase slug, such as "build-orchestrator".
  - Epic ids: "E1", "E2", "E3".
  - Story ids: "E1.S1", "E1.S2", "E2.S1".
- Use "planned" as the default status unless the prompt clearly indicates another status.
- Make epics independently useful delivery areas.
- Make stories concrete enough that an implementer can start work without rereading the original discussion.
- Acceptance criteria must be observable, not vague.
- Unit tests should name the behavior being tested. If testing is not applicable, include a manual or smoke test instead.
- recommendedOrder should reference story IDs, not epic IDs, unless the plan truly only has epic-level sequencing.
- exitCriteria should describe the final proof that the entire plan succeeded.
- changedFiles is required. Every plan must list the files that will be changed, using the FileTree shape below.
- Format local file references in Markdown fields ("epic.description", "story.description", "metadata") as Markdown links such as [Runtime entry — line 42, `fn run`](/abs/path/to/file.zig) or [src/cli.zig](src/cli.zig). The UI automatically renders local paths (/Users/..., ./..., ../..., ~...) as click-to-copy buttons and wraps fenced code blocks with a language/copy toolbar.

Optional fields may be included when useful:

Top-level optional fields:
- "heroTitle": string or { "lead": string, "accent"?: string }. Customizes the Overview hero headline (with "accent" rendered in italic accent color). When omitted, the UI splits "title" automatically.
- "firstStorySummary": string. Customizes the body copy of the Overview "Recommended start" card. When omitted, the UI extracts the first sentence of the first recommended story's details or description.
- "generatedAt": ISO-8601 date-time string.
- "scope": short text describing the plan scope (displayed as the hero lede).
- "metadata": object with extra context (rendered in the Architecture & decisions view).
- "sections": typed non-story decision/architecture cards rendered in the Architecture & decisions view.

Epic optional fields:
- "shortTitle": short 2–4 word label used in the Overview epic index list. Falls back to "title" when omitted.
- "summary": short pitch shown on the epic card header and Overview epic index.
- "description": Markdown string rendered inside the epic card's collapsible "Design reference & examples" drawer. Use this for target code examples, design notes, and reference links.
- "status": one of "draft", "planned", "ready", "in-progress", "blocked", "complete", "archived".
- "dependencies": array of referenced epic or story IDs.

Story optional fields:
- "status": one of "draft", "planned", "ready", "in-progress", "blocked", "complete", "archived".
- "risk": one of "low", "medium", "high", "critical".
- "dependencies": array of referenced story IDs.
- "description": Markdown string rendered inside the story reader modal's collapsible "Design & source references" drawer. Use this for links to existing source files, line numbers, and design targets rather than duplicating implementation steps from "details".
- "details": array of concrete implementation steps.
- "acceptanceCriteria": array of observable completion checks.
- "unitTests": array of tests to add or run.
- "filesLikelyTouched": array of repo-relative paths or module names.

FileTree shape:
- "label": optional string. Heading for a single tree (e.g. "Source", "Tests").
- "root": required FileTreeNode.

FileTreeNode shape:
- "name": required string. Display name of the file or folder.
- "type": required, one of "folder" or "file".
- "status": optional, one of "new" or "modified". Only valid on file nodes. Folders derive change state from their descendants and must not carry a status.
- "stories": optional array of story IDs (e.g. ["E1.S1", "E2.S3"]). Only valid on file nodes. Lists which stories touch this file.
- "children": required for folder nodes, absent for file nodes. Array of FileTreeNode.

Prefer concise, dense plans. Avoid filler. Do not invent exact file paths, commands, APIs, or dates unless they were provided or are obvious from context.
